# Comic Reader — Data Model

> **Status:** Proposed schema, for review. Nothing in this document is implemented.
> **Companion documents:** [`ARCHITECTURE.md`](./ARCHITECTURE.md), [`ROADMAP.md`](./ROADMAP.md).
> **Target:** SQLite 3 with `PRAGMA foreign_keys = ON`, WAL journaling.

---

## 1. Design principles

1. **Files and catalog identities are separate.** A `library_file` can exist, be read, and hold
   progress without belonging to any `issue`. `file_issue_map` connects them when a match is
   known or confirmed. This is the single most important property of the schema.
2. **Reading orders are independent of series.** An order item points at an `issue` (or a bare
   file), not at a series. Issues carry their own publisher through `series`, so an order can
   freely mix publishers, imprints, and eras.
3. **Spoilers are data, not presentation.** Any stored fact that can reveal story information
   carries a *reveal anchor* (an issue, or an order position). Queries filter on it in SQL.
4. **Provenance is explicit.** Imported metadata is never silently merged. Every field can be
   traced to a source, a fetch time, and a confidence, and user edits are marked as such.
5. **Stable identifiers.** Integer primary keys for joins; UUIDs for anything that may be
   exported, relinked, imported from a friend, or synchronised later.
6. **Additive growth.** New domains (locations, reading sessions, sync) should be new tables and
   indexes, not rewrites of the core. Avoid polymorphic columns in the core; use them only where
   the alternative is a combinatorial explosion and document the lost integrity.
7. **Soft delete for user data, hard delete for derived data.** `deleted_at` preserves progress,
   collections, and order history. Caches and rebuildable projections can be dropped.
8. **Partial dates are normal.** Comic cover dates are frequently month-only or year-only. Store
   them as ISO-8601 text and tolerate reduced precision.

### 1.1 Consequences that must be accepted

- A file can map to zero, one, or many issues. Progress is stored per file; issue status is a
  separate, explicitly reconciled record. This dual model is necessary but requires one rule:
  **file progress is the source of truth for "where I am"; issue status is the source of truth
  for "have I read this".**
- The schema allows duplicate-looking issues (same number, different variant/suffix) and
  duplicate-looking creators (same name). Identity is established by external IDs and manual
  confirmation, not by a unique name constraint.
- Contrary to a common shortcut, `issues` is not the root of the library. `library_files` is.

## 2. Conventions

| Convention | Choice |
| --- | --- |
| Primary keys | `INTEGER PRIMARY KEY` (rowid alias) |
| Public identifiers | `uuid TEXT NOT NULL UNIQUE`, lowercase v4/v7 UUID generated by Rust |
| Timestamps | `INTEGER` milliseconds since Unix epoch, UTC |
| Calendar dates | `TEXT` ISO-8601, `YYYY-MM-DD` or reduced precision (`YYYY-MM`, `YYYY`) |
| Booleans | `INTEGER` 0/1 with `CHECK (x IN (0,1))` |
| Enumerations | `TEXT` with `CHECK` constraints; open vocabularies get lookup tables |
| Case-insensitive names | Store display form plus a normalised `sort_name`/`name_norm` |
| Soft delete | `deleted_at INTEGER NULL`; partial indexes exclude deleted rows |
| Migrations | `schema_migrations` table plus `PRAGMA user_version` |
| JSON | Only for opaque payloads (provider snapshots, layout preferences, rules). Never for data that is queried relationally. |

SQLite does not have a native boolean, datetime, UUID, or enum type. The checks above are the
substitute; they must be enforced consistently in application code as well.

## 4. Shared asset table

Cover art, character portraits, and collection images are stored through one asset table so the
UI has a single image-loading path.

```sql
CREATE TABLE assets (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  kind          TEXT NOT NULL CHECK (kind IN (
                  'cover','character','creator','collection','arc','event',
                  'provider','user','placeholder')),
  storage       TEXT NOT NULL CHECK (storage IN (
                  'cache_file',   -- file under app_cache_dir, content-addressed
                  'remote',       -- provider URL; must be cached before display
                  'embedded')),   -- bytes extracted from a library file
  rel_path      TEXT,             -- relative to cache dir, for storage='cache_file'
  remote_url    TEXT,
  mime_type     TEXT,
  width         INTEGER,
  height        INTEGER,
  byte_size     INTEGER,
  content_hash  TEXT,             -- BLAKE3 of the bytes
  source_id     INTEGER REFERENCES metadata_sources(id),
  created_at    INTEGER NOT NULL,
  CHECK (
    (storage = 'cache_file' AND rel_path IS NOT NULL) OR
    (storage = 'remote'     AND remote_url IS NOT NULL) OR
    (storage = 'embedded'   AND content_hash IS NOT NULL)
  )
);

CREATE INDEX ix_assets_hash ON assets(content_hash);
```

Notes and criticisms:

- `storage='remote'` is deliberately not directly renderable. The architecture requires provider
  images to be downloaded and cached in Rust, otherwise offline mode and CSP break.
- `metadata_sources` is created in §12; SQLite tolerates the forward reference, but migrations
  should create referenced tables first in practice.
- Deduplicate assets by `content_hash` before insert; a unique partial index is possible but
  would reject legitimate multi-source duplicates. Application-level dedupe is preferred.

## 5. Publishers, franchises, series

### 5.1 Publishers and imprints

```sql
CREATE TABLE publishers (
  id           INTEGER PRIMARY KEY,
  uuid         TEXT NOT NULL UNIQUE,
  name         TEXT NOT NULL,
  sort_name    TEXT,
  short_name   TEXT,
  parent_id    INTEGER REFERENCES publishers(id),  -- imprint or subsidiary
  country_code TEXT,
  founded_year INTEGER,
  description  TEXT,
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  deleted_at   INTEGER
);

CREATE INDEX ix_publishers_parent ON publishers(parent_id);
```

**Why `parent_id` rather than a separate `imprints` table:** imprints behave exactly like
publishers for display and filtering, and a self-reference avoids two near-identical tables. A
series is published by exactly one publisher row; an imprint is that row.

**Problem:** real bibliographic data changes hands (a series may move from one publisher to
another, or be reprinted). Do not encode "current publisher" as immutable. If this becomes
important, add `series_publisher_periods` later; it is an additive migration, not a rewrite.

### 5.2 Franchises / continuities (optional but recommended)

A reading order can span publishers; a *franchise* is the shared fictional continuity that makes
that meaningful (for example, a licensed universe with several publishers, or a creator-owned
shared world). This is not the same as a publisher and not the same as a story arc.

```sql
CREATE TABLE franchises (
  id          INTEGER PRIMARY KEY,
  uuid        TEXT NOT NULL UNIQUE,
  name        TEXT NOT NULL,
  description TEXT,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);

CREATE TABLE franchise_series (
  franchise_id INTEGER NOT NULL REFERENCES franchises(id) ON DELETE CASCADE,
  series_id    INTEGER NOT NULL REFERENCES series(id)    ON DELETE CASCADE,
  is_primary   INTEGER NOT NULL DEFAULT 0 CHECK (is_primary IN (0,1)),
  PRIMARY KEY (franchise_id, series_id)
);
```

A reading order does **not** require a franchise. The column exists so timelines and curated
orders can be scoped later without reshaping `reading_orders`.

### 5.3 Series

```sql
CREATE TABLE series (
  id               INTEGER PRIMARY KEY,
  uuid             TEXT NOT NULL UNIQUE,
  publisher_id     INTEGER NOT NULL REFERENCES publishers(id),
  franchise_id     INTEGER REFERENCES franchises(id),
  parent_series_id INTEGER REFERENCES series(id),   -- relaunch / volume grouping
  title            TEXT NOT NULL,
  sort_title       TEXT NOT NULL,
  subtitle         TEXT,
  volume           INTEGER,                          -- "Batman (2016)" -> 3, etc.
  start_year       INTEGER,
  end_year         INTEGER,
  status           TEXT NOT NULL DEFAULT 'unknown' CHECK (status IN (
                     'ongoing','completed','hiatus','cancelled',
                     'limited','one_shot','unknown')),
  series_type      TEXT NOT NULL DEFAULT 'ongoing' CHECK (series_type IN (
                     'ongoing','limited','one_shot','annual','graphic_novel',
                     'trade','webcomic','anthology','unknown')),
  country_code     TEXT,
  language_code    TEXT,
  description      TEXT,
  cover_asset_id   INTEGER REFERENCES assets(id),
  metadata_locked  INTEGER NOT NULL DEFAULT 0 CHECK (metadata_locked IN (0,1)),
  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  deleted_at       INTEGER
);

CREATE INDEX ix_series_publisher ON series(publisher_id, sort_title);
CREATE INDEX ix_series_franchise ON series(franchise_id);
CREATE INDEX ix_series_parent    ON series(parent_series_id);
CREATE INDEX ix_series_sort      ON series(sort_title) WHERE deleted_at IS NULL;
```

**Criticisms and decisions:**

- **No unique constraint on `(publisher, title, volume)`.** Comic metadata is messy: reboots,
  renumbering, same title in two imprints, foreign editions. A unique index would reject valid
  data and force users to mangle titles. Identity is enforced through `external_ids` and manual
  confirmation instead.
- **`series_type='trade'` is a compromise.** Collected editions are structurally close to series
  but are often modelled as a separate "collected edition" concept. Keeping them in `series` with
  a type is simpler for v1; if trade/omnibus navigation diverges, add `collected_editions` later.
- `parent_series_id` groups volumes but does not impose an ordering. Ordering belongs in a
  reading order.

### 5.4 Issues

```sql
CREATE TABLE issues (
  id                    INTEGER PRIMARY KEY,
  uuid                  TEXT NOT NULL UNIQUE,
  series_id             INTEGER NOT NULL REFERENCES series(id),
  issue_number          TEXT NOT NULL,              -- display form: "1", "0", "1/2", "Annual 1"
  issue_number_sort     REAL,                       -- numeric sort key; NULL if not numeric
  suffix                TEXT NOT NULL DEFAULT '',   -- variant / edition suffix
  title                 TEXT,
  subtitle              TEXT,
  volume                INTEGER,
  cover_date            TEXT,                       -- ISO-8601, reduced precision allowed
  store_date            TEXT,
  release_date          TEXT,
  page_count            INTEGER,
  synopsis              TEXT,                       -- spoiler-sensitive; see §13
  synopsis_reveal_issue_id INTEGER REFERENCES issues(id),
  cover_asset_id        INTEGER REFERENCES assets(id),
  is_variant_of         INTEGER REFERENCES issues(id),
  story_title           TEXT,
  rating                TEXT,
  notes                 TEXT,
  metadata_locked       INTEGER NOT NULL DEFAULT 0 CHECK (metadata_locked IN (0,1)),
  created_at            INTEGER NOT NULL,
  updated_at            INTEGER NOT NULL,
  deleted_at            INTEGER
);

CREATE UNIQUE INDEX ux_issues_identity
  ON issues(series_id, issue_number, suffix)
  WHERE deleted_at IS NULL;

CREATE INDEX ix_issues_series_sort
  ON issues(series_id, issue_number_sort, issue_number)
  WHERE deleted_at IS NULL;

CREATE INDEX ix_issues_cover_date ON issues(cover_date) WHERE deleted_at IS NULL;
CREATE INDEX ix_issues_variant    ON issues(is_variant_of) WHERE is_variant_of IS NOT NULL;
```

**Numbering is text plus a numeric sort key.** `issue_number` must never be an integer: specials,
`-1`, `0`, `1/2`, `½`, `Annual 1`, `1000000`, and decimal renumberings all occur.
`issue_number_sort` is nullable because not every number is numeric; sorting falls back to
natural order on the text.

**Variants.** A variant cover is represented as a separate `issue` with the same number and a
distinct `suffix` (for example `''` for the standard cover, `'B'` for a variant). `is_variant_of`
links it to the standard issue. This keeps variant covers out of reading orders unless explicitly
added. Alternative considered: a separate `issue_variants` table. It would duplicate credits and
metadata per variant; the suffix approach is lighter. **Decision needed (Q2).**

**Issue without a series.** Not allowed in the catalog. A publisher one-shot still gets a series
row of type `one_shot`. Files without any catalog identity remain `library_files` and are not
forced into an issue.

### 5.5 Creators and credits

```sql
CREATE TABLE creators (
  id           INTEGER PRIMARY KEY,
  uuid         TEXT NOT NULL UNIQUE,
  name         TEXT NOT NULL,
  sort_name    TEXT NOT NULL,
  birth_year   INTEGER,
  death_year   INTEGER,
  country_code TEXT,
  bio          TEXT,
  image_asset_id INTEGER REFERENCES assets(id),
  metadata_locked INTEGER NOT NULL DEFAULT 0 CHECK (metadata_locked IN (0,1)),
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  deleted_at   INTEGER
);

CREATE INDEX ix_creators_sort ON creators(sort_name) WHERE deleted_at IS NULL;

CREATE TABLE issue_credits (
  id          INTEGER PRIMARY KEY,
  uuid        TEXT NOT NULL UNIQUE,
  issue_id    INTEGER NOT NULL REFERENCES issues(id)   ON DELETE CASCADE,
  creator_id  INTEGER NOT NULL REFERENCES creators(id),
  role        TEXT NOT NULL,        -- open vocabulary, see note
  credited_as TEXT NOT NULL DEFAULT '',  -- name as printed; '' means same as creator.name
  sequence    INTEGER NOT NULL DEFAULT 0,
  source_id   INTEGER REFERENCES metadata_sources(id),
  created_at  INTEGER NOT NULL,
  UNIQUE (issue_id, creator_id, role, credited_as)
);

CREATE INDEX ix_credits_issue   ON issue_credits(issue_id);
CREATE INDEX ix_credits_creator ON issue_credits(creator_id, role);
```

**Role is an open vocabulary**, not a `CHECK` list. Comic credits change by era, country, and
publisher (`plot`, `script`, `breakdowns`, `finishes`, `colour`, `translation`, `letterer`,
`editor-in-chief`). Constrain it in application code and provide an autocomplete; a table is
unnecessary until role display/translation is needed.

**Creator identity is genuinely hard.** Two people can share a name; one person can be credited
under multiple names. Do not unique `creators.name`. Use `external_ids` and a manual merge tool
(later). A merge must reassign `issue_credits`, not delete credited data. Splitting a creator is
more painful; plan for it.

## 6. Library, files, and pages

### 6.1 Library roots

```sql
CREATE TABLE library_roots (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  display_name  TEXT NOT NULL,
  path          TEXT NOT NULL UNIQUE,   -- canonical absolute path
  path_kind     TEXT NOT NULL DEFAULT 'directory'
                CHECK (path_kind IN ('directory','single_file')),
  scan_mode     TEXT NOT NULL DEFAULT 'manual'
                CHECK (scan_mode IN ('manual','watch')),
  is_read_only  INTEGER NOT NULL DEFAULT 1 CHECK (is_read_only IN (0,1)),
  last_scan_at  INTEGER,
  last_scan_status TEXT CHECK (last_scan_status IN (
                  'never','running','completed','cancelled','failed')),
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted_at    INTEGER
);

CREATE INDEX ix_roots_active ON library_roots(path) WHERE deleted_at IS NULL;
```

`is_read_only` is a statement of policy: the scanner does not write to comic files. Should a
future "normalise library" feature exist, it must be a separate, explicit flow.

### 6.2 Library files

```sql
CREATE TABLE library_files (
  id                INTEGER PRIMARY KEY,
  uuid              TEXT NOT NULL UNIQUE,
  root_id           INTEGER NOT NULL REFERENCES library_roots(id),
  rel_path          TEXT NOT NULL,             -- '/'-separated, relative to root
  display_name      TEXT NOT NULL,
  format            TEXT NOT NULL CHECK (format IN (
                      'cbz','zip','cbr','rar','cb7','7z','folder','pdf','image','unknown')),
  byte_size         INTEGER NOT NULL DEFAULT 0,
  mtime_ms          INTEGER,
  quick_fingerprint TEXT,                      -- size + mtime + head/tail hash
  content_hash      TEXT,                      -- full BLAKE3, may be NULL until computed
  page_count        INTEGER,
  cover_page_index  INTEGER,                   -- NULL = use first page
  status            TEXT NOT NULL DEFAULT 'pending' CHECK (status IN (
                      'pending','indexing','indexed','unreadable','missing','ignored')),
  status_detail     TEXT,                      -- safe error code, not a stack trace
  problem_count     INTEGER NOT NULL DEFAULT 0,
  scanned_at        INTEGER,
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL,
  deleted_at        INTEGER,
  UNIQUE (root_id, rel_path)
);

CREATE INDEX ix_files_root       ON library_files(root_id, rel_path);
CREATE INDEX ix_files_status     ON library_files(status) WHERE deleted_at IS NULL;
CREATE INDEX ix_files_hash       ON library_files(content_hash) WHERE content_hash IS NOT NULL;
CREATE INDEX ix_files_fingerprint ON library_files(quick_fingerprint);
```

**Important design properties:**

- **`rel_path` is the identity within a root.** If a root is moved, only
  `library_roots.path` changes.
- **`content_hash` is the portable identity across roots.** It enables duplicate detection and
  move detection. It is nullable because hashing a huge library is slow and must be incremental.
- **`folder` is a format**, because a directory of images is a first-class reading unit. The
  page manifest for a folder is materialised in `file_pages` just like an archive's.
- **No absolute path column.** Any code that needs a path reconstructs it from
  `library_roots.path` plus `rel_path` after validation. This is deliberate.
- **`status='missing'` instead of deleting.** A temporarily unmounted drive must not destroy
  progress and collections. Missing files are reconciled later.

**Criticism:** `UNIQUE(root_id, rel_path)` breaks on case-sensitive vs case-insensitive
filesystems if paths are normalised inconsistently. Store paths exactly as discovered, but add a
normalised comparison column later if duplicate-by-case files occur. Do not lowercase paths
globally; Linux allows distinct files differing only by case.

### 6.3 File pages (page manifest)

```sql
CREATE TABLE file_pages (
  file_id         INTEGER NOT NULL REFERENCES library_files(id) ON DELETE CASCADE,
  page_index      INTEGER NOT NULL,            -- 0-based display order
  entry_name      TEXT NOT NULL,               -- archive entry or folder filename
  width           INTEGER,
  height          INTEGER,
  mime_type       TEXT,
  byte_size       INTEGER,
  is_double_page  INTEGER NOT NULL DEFAULT 0 CHECK (is_double_page IN (0,1)),
  is_cover        INTEGER NOT NULL DEFAULT 0 CHECK (is_cover IN (0,1)),
  content_hash    TEXT,
  PRIMARY KEY (file_id, page_index)
);

CREATE INDEX ix_pages_dimensions ON file_pages(file_id, width, height);
```

- The manifest is rebuilt when the file's fingerprint changes, inside a transaction, so the file
  never has a partially updated page list.
- `page_index` is a physical page counter, not a story reference. Double-page detection is a
  hint that the reader can override per file.
- Storing `entry_name` is necessary because archives are read by entry, not by numeric index,
  and because a rescan can confirm that names have not changed.

### 6.4 File ↔ issue mapping

```sql
CREATE TABLE file_issue_map (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  file_id       INTEGER NOT NULL REFERENCES library_files(id) ON DELETE CASCADE,
  issue_id      INTEGER NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
  match_kind    TEXT NOT NULL CHECK (match_kind IN (
                  'manual','filename','comicinfo','provider','import')),
  confidence    REAL NOT NULL DEFAULT 1.0 CHECK (confidence BETWEEN 0 AND 1),
  is_primary    INTEGER NOT NULL DEFAULT 1 CHECK (is_primary IN (0,1)),
  page_offset   INTEGER NOT NULL DEFAULT 0,    -- first file page that belongs to this issue
  page_count    INTEGER,                        -- NULL = to end of file
  confirmed_by_user INTEGER NOT NULL DEFAULT 0 CHECK (confirmed_by_user IN (0,1)),
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  UNIQUE (file_id, issue_id)
);

CREATE INDEX ix_map_issue ON file_issue_map(issue_id);
CREATE INDEX ix_map_file  ON file_issue_map(file_id);
```

**Why many-to-many is required, despite its cost:**

- One file can contain several issues (an omnibus, a scanned "pack", a double-issue).
  `page_offset`/`page_count` carve the file into issue segments.
- One issue can have several files (a split scan, a colour and a scanlation copy, a broken file
  superseded by a re-download).
- Storing the mapping separately from both sides means relinking a file does not touch progress,
  and rematching an issue does not duplicate progress.

**`is_primary`** designates the copy the reader opens by default when an issue has multiple
files. A partial unique index can enforce one primary per issue:

```sql
CREATE UNIQUE INDEX ux_map_primary_issue
  ON file_issue_map(issue_id)
  WHERE is_primary = 1;
```

This is recommended, but evaluate the UX for "two equally good copies" — users may want several
primaries for different reading modes. **Decision Q3.**

**`page_offset` / `page_count` is the fragile part.** Progress is stored against the file page
index, and issue-level position is derived through the mapping. If the mapping changes after the
user has read, derived issue progress can shift. Mitigation: when a mapping changes, recompute
affected issue progress explicitly and record the change; never silently reinterpret saved page
indices. This is one of the most important rules in the model.

### 6.5 Scan jobs (optional persistence)

Jobs are runtime state. Persisting them is only useful for resumable scans and diagnostics:

```sql
CREATE TABLE scan_jobs (
  id           INTEGER PRIMARY KEY,
  uuid         TEXT NOT NULL UNIQUE,
  root_id      INTEGER REFERENCES library_roots(id),
  kind         TEXT NOT NULL CHECK (kind IN ('scan','reindex','hash','thumbnail','metadata')),
  status       TEXT NOT NULL CHECK (status IN ('queued','running','cancelled','failed','done')),
  progress     REAL NOT NULL DEFAULT 0 CHECK (progress BETWEEN 0 AND 1),
  total_items  INTEGER,
  done_items   INTEGER NOT NULL DEFAULT 0,
  error_code   TEXT,
  started_at   INTEGER,
  finished_at  INTEGER,
  created_at   INTEGER NOT NULL
);
```

Do not store per-file job rows indefinitely; that table becomes a log. Keep only recent jobs, or
delete completed jobs at startup.

## 7. Reading progress and bookmarks

### 7.1 Reader profiles

Spoiler protection, reading position, and preferences only make sense relative to a reader. Even
a single-user application should model the profile, because spoiler rules differ per person in a
household and because future sync needs a namespace.

```sql
CREATE TABLE reader_profiles (
  id                  INTEGER PRIMARY KEY,
  uuid                TEXT NOT NULL UNIQUE,
  name                TEXT NOT NULL,
  is_default          INTEGER NOT NULL DEFAULT 0 CHECK (is_default IN (0,1)),
  avatar_asset_id     INTEGER REFERENCES assets(id),
  spoiler_mode        TEXT NOT NULL DEFAULT 'strict' CHECK (spoiler_mode IN (
                        'off','strict','covers_only','custom')),
  spoiler_sources     TEXT NOT NULL DEFAULT '["synopsis","characters","arcs","events"]',
  created_at          INTEGER NOT NULL,
  updated_at          INTEGER NOT NULL,
  deleted_at          INTEGER
);

CREATE UNIQUE INDEX ux_profile_default
  ON reader_profiles(is_default) WHERE is_default = 1;
```

`spoiler_sources` is a JSON array of *fact domains* to hide. It is deliberately open-ended so new
spoiler-capable domains can be added without a migration. It is not queried relationally; it is a
policy blob. Keep the filtering logic in Rust.

### 7.2 File reading progress

```sql
CREATE TABLE reading_progress (
  profile_id       INTEGER NOT NULL REFERENCES reader_profiles(id) ON DELETE CASCADE,
  file_id          INTEGER NOT NULL REFERENCES library_files(id) ON DELETE CASCADE,
  last_page_index  INTEGER NOT NULL DEFAULT 0,
  furthest_page_index INTEGER NOT NULL DEFAULT 0,
  scroll_offset    REAL,                   -- 0..1 within page, for continuous modes
  zoom             REAL,
  reading_mode     TEXT,                   -- optional last-used mode
  completed_at     INTEGER,
  last_read_at     INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  PRIMARY KEY (profile_id, file_id),
  CHECK (last_page_index >= 0),
  CHECK (furthest_page_index >= 0)
);

CREATE INDEX ix_progress_profile_recent
  ON reading_progress(profile_id, last_read_at DESC);
CREATE INDEX ix_progress_file ON reading_progress(file_id);
```

**Why file-level, not issue-level, is canonical:** a file may be unmatched, a file may map to
several issues, and a file may be replaced. The file is what the user actually reads. Issue status
is derived and reconciled through the mapping (§7.3).

**Why both `last_page_index` and `furthest_page_index`:** "resume where I am" and "how much have
I read" are different questions. Re-reading a page must not reduce progress statistics; jumping
backwards must not erase completion. Any statistics feature depends on this distinction.

**`scroll_offset` and `zoom` are per-file**, not global preferences. Per-series and global
defaults belong in `reader_profiles`/`preferences`; a file-level override wins.

### 7.3 Issue progress (derived but persisted)

```sql
CREATE TABLE issue_progress (
  profile_id      INTEGER NOT NULL REFERENCES reader_profiles(id) ON DELETE CASCADE,
  issue_id        INTEGER NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
  status          TEXT NOT NULL DEFAULT 'unread' CHECK (status IN (
                    'unread','reading','completed','skipped','dropped')),
  last_page_index INTEGER,
  completed_at    INTEGER,
  started_at      INTEGER,
  status_source   TEXT NOT NULL DEFAULT 'derived' CHECK (status_source IN (
                    'derived','manual','import')),
  updated_at      INTEGER NOT NULL,
  PRIMARY KEY (profile_id, issue_id)
);

CREATE INDEX ix_issue_progress_status ON issue_progress(profile_id, status);
```

**This is intentionally redundant.** It could be computed from `reading_progress` and
`file_issue_map`, but:

- spoiler queries need fast "has this profile read this issue?" lookups;
- reading-order progress needs an issue-level frontier;
- a user may mark an issue as read without reading a file (a physical copy), or skip it.

The reconciliation rule:

1. Reading a file updates `reading_progress`.
2. A trigger or service writes `issue_progress` for each mapped issue whose segment is covered.
3. Manual status changes write `issue_progress` directly and are marked as manual so automatic
   reconciliation does not overwrite them.

SQLite triggers can do simple propagation, but **do not put complex reconciliation in triggers**.
Use a Rust service in the same transaction; triggers that call non-deterministic logic are hard to
test and migrate.

### 7.4 Bookmarks and annotations

CREATE TABLE bookmarks (
  id          INTEGER PRIMARY KEY,
  uuid        TEXT NOT NULL UNIQUE,
  profile_id  INTEGER NOT NULL REFERENCES reader_profiles(id) ON DELETE CASCADE,
  file_id     INTEGER NOT NULL REFERENCES library_files(id) ON DELETE CASCADE,
  page_index  INTEGER NOT NULL,
  label       TEXT,
  note        TEXT,
  color       TEXT,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);

CREATE INDEX ix_bookmarks_file ON bookmarks(profile_id, file_id, page_index);

CREATE TABLE annotations (
  id            INTEGER PRIMARY KEY,

  bookmark_id   INTEGER NOT NULL REFERENCES bookmarks(id) ON DELETE CASCADE,

**Critical spoiler note:** a bookmark label or note can itself spoil (for example "the death of

bookmarks and collection descriptions need the same spoiler treatment as other text.

## 8. Reading orders (independent of series)

This is the feature most likely to be modelled badly. A reading order is **an ordered list of
references**, plus progress tracking for a profile. It is not a property of a series, and it is
not `issues.position`.

### 8.1 Order tables

```sql
CREATE TABLE reading_orders (
  id               INTEGER PRIMARY KEY,
  uuid             TEXT NOT NULL UNIQUE,
  title            TEXT NOT NULL,
  description      TEXT,
  franchise_id     INTEGER REFERENCES franchises(id),
  order_type       TEXT NOT NULL DEFAULT 'custom' CHECK (order_type IN (
                     'chronological','publication','story_arc','character',
                     'event','recommended','custom','imported')),
  spoiler_safe     INTEGER NOT NULL DEFAULT 1 CHECK (spoiler_safe IN (0,1)),
  is_shareable     INTEGER NOT NULL DEFAULT 0 CHECK (is_shareable IN (0,1)),
  source_url       TEXT,                     -- attribution for imported orders
  source_author    TEXT,
  created_by_profile_id INTEGER REFERENCES reader_profiles(id),
  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  deleted_at       INTEGER
);

CREATE INDEX ix_orders_franchise ON reading_orders(franchise_id) WHERE deleted_at IS NULL;

CREATE TABLE reading_order_items (
  id              INTEGER PRIMARY KEY,
  uuid            TEXT NOT NULL UNIQUE,
  order_id        INTEGER NOT NULL REFERENCES reading_orders(id) ON DELETE CASCADE,
  position        REAL NOT NULL,            -- gaps allow cheap reordering
  issue_id        INTEGER REFERENCES issues(id),
  file_id         INTEGER REFERENCES library_files(id),
  group_label     TEXT,                     -- "Act I", "Before the war"
  note            TEXT,                      -- can be spoiler-sensitive
  is_optional     INTEGER NOT NULL DEFAULT 0 CHECK (is_optional IN (0,1)),
  is_section_break INTEGER NOT NULL DEFAULT 0 CHECK (is_section_break IN (0,1)),
  created_at      INTEGER NOT NULL,
  CHECK (issue_id IS NULL OR file_id IS NULL),
  CHECK (
    issue_id IS NOT NULL OR file_id IS NOT NULL OR
    (is_section_break = 1 AND group_label IS NOT NULL)
  )
);

CREATE INDEX ix_order_items_order ON reading_order_items(order_id, position);
CREATE INDEX ix_order_items_issue ON reading_order_items(issue_id);
CREATE INDEX ix_order_items_file  ON reading_order_items(file_id);

CREATE TABLE reading_order_progress (
  profile_id      INTEGER NOT NULL REFERENCES reader_profiles(id) ON DELETE CASCADE,
  order_id        INTEGER NOT NULL REFERENCES reading_orders(id) ON DELETE CASCADE,
  last_item_id    INTEGER REFERENCES reading_order_items(id),
  furthest_position REAL,
  completed_at    INTEGER,
  updated_at      INTEGER NOT NULL,
  PRIMARY KEY (profile_id, order_id)
);
```

### 8.2 Why `position REAL` and not `position INTEGER`

Reordering a 500-item list with integer positions rewrites every row after the moved item. With
gaps of 1024, inserting between two items is one update; rebalancing is rare. Alternative: a
fractional-index string (LexoRank-style). Real numbers are simpler and sufficient until
float precision becomes a problem (roughly 50 consecutive inserts between the same pair); at that
point renormalise the affected slice. **This is a recommendation (R13), not a certainty.**

### 8.3 Why items can point at an issue *or* a file

- A curated order should reference **issues**, so progress is shared across copies and the order
  survives a file being replaced.
- A personal order may need to reference an **unmatched file** (a webcomic chapter, a doujin, a
  scan with no catalog identity). Forcing it into `issues` would pollute the catalog.

Forcing one of these two would either break unmatched content or create fake issues. The XOR
check constraint keeps the invariant explicit, and section breaks are allowed with only a label.

**Do not enforce "an issue appears at most once per order" by default.** It looks sensible, but
curated orders legitimately repeat an issue (a flash-forward issue read twice, a "previously on"
recap that is itself an issue, a re-read checkpoint). If duplicates are disallowed later, add a
partial unique index; starting with one rejects real orders and is hard to undo without data loss.

### 8.4 Chronological orders across publishers

Nothing in `reading_order_items` references a publisher. Chronology is expressed by item order,
optionally annotated with:

- `group_label` for era/act grouping,
- an `order_type='chronological'` and a franchise scope,
- issue-level `story_start_date` / `story_end_date` on `issues` if in-universe dating is needed.

**Proposed addition for in-universe chronology:**

```sql
ALTER TABLE issues ADD COLUMN story_start_date TEXT;  -- ISO-8601, reduced precision allowed
ALTER TABLE issues ADD COLUMN story_end_date   TEXT;
```

These are *story* dates, distinct from `cover_date`/`store_date` (publication). Without them,
"chronological" can only mean "curated sequence". Automated chronology from story dates is
unreliable when a flashback or a time-travel arc is involved, so treat any generated chronology
as a draft that a user confirms. **Decision Q4.**

### 8.5 Conflicts when orders disagree

Two popular orders will disagree. The model supports this by keeping orders independent; it does
not try to merge them. There is no single "chronological" truth. UI must let a user choose an
order, not imply one canonical sequence.

### 8.6 Import and export

`reading_orders` + items can be exported as versioned JSON with UUIDs and external identifiers.
On import:

- resolve external IDs first,
- fall back to series title + issue number,
- leave unresolved items visible as placeholders rather than dropping them.

A dropped item silently changes the order; do not drop. Unresolved placeholders also solve the
"order imported before the library is complete" case.

## 9. Custom collections

Collections are user-curated sets. They are not reading orders: order inside a collection is
secondary, and membership is not progress-tracked.

```sql
CREATE TABLE collections (
  id          INTEGER PRIMARY KEY,
  uuid        TEXT NOT NULL UNIQUE,
  name        TEXT NOT NULL,
  description TEXT,
  cover_asset_id INTEGER REFERENCES assets(id),
  is_smart    INTEGER NOT NULL DEFAULT 0 CHECK (is_smart IN (0,1)),
  smart_rules TEXT,                  -- JSON, only when is_smart = 1
  sort_mode   TEXT NOT NULL DEFAULT 'manual' CHECK (sort_mode IN (
                'manual','title','added_desc','added_asc','release_date')),
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);

CREATE TABLE collection_items (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  collection_id INTEGER NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
  entity_type   TEXT NOT NULL CHECK (entity_type IN (
                  'series','issue','arc','event','character','order','file')),
  entity_id     INTEGER NOT NULL,
  position      REAL,
  note          TEXT,
  added_at      INTEGER NOT NULL
);

CREATE INDEX ix_collection_items_coll ON collection_items(collection_id, position);
CREATE INDEX ix_collection_items_entity ON collection_items(entity_type, entity_id);
```

**Criticism of the polymorphic `entity_type`/`entity_id`:** SQLite cannot enforce a foreign key to
six different tables. Orphaned rows are possible and deletes must be cleaned by the application.
The alternatives are:

- six nullable FK columns with a check — verbose but fully enforced;
- one join table per entity type — most correct, but six tables and more code.

For a modest feature, the polymorphic table with application-level integrity and a periodic
orphan cleanup is a reasonable trade-off. Document it; do not pretend it is enforced. If
collections become central (smart collections over the whole catalog), move to explicit join
tables via an additive migration.

**Smart collections** need a rules engine. `smart_rules` JSON is a trap if it grows into a
query language. Recommendation: support a fixed, typed rule set (publisher, series, tag, read
status, year range) and compile it to SQL in Rust with an allowlist. Do not evaluate arbitrary
user expressions.

## 10. Characters and appearances

Character data is mostly a LATER face, but the minimal tables must exist now if arcs and spoiler
protection reference characters.

> **Implemented as of schema v11** — a deliberately narrower shape than the design below:
> `characters` is scoped by `series_id` (unique per `(series_id, name)`) and carries
> `description_source` (`comic`/`web`/`manual`) plus `source_url`; `character_appearances` links
> character to issue with a `source` (`comicinfo`/`manual`). There is no `assets`/portrait
> column, no `appearance_type`, and no `is_death`/`is_return`/`is_first_appearance` yet.
> `character_relationships` is still unimplemented. Cross-series identity is unresolved: the
> same character in two series is two rows.

### 10.1 Characters

```sql
CREATE TABLE characters (
  id           INTEGER PRIMARY KEY,
  uuid         TEXT NOT NULL UNIQUE,
  name         TEXT NOT NULL,
  sort_name    TEXT NOT NULL,
  real_name    TEXT,
  description  TEXT,
  image_asset_id INTEGER REFERENCES assets(id),
  first_appearance_issue_id INTEGER REFERENCES issues(id),
  is_public_domain INTEGER NOT NULL DEFAULT 0 CHECK (is_public_domain IN (0,1)),
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  deleted_at   INTEGER
);

CREATE INDEX ix_characters_sort ON characters(sort_name) WHERE deleted_at IS NULL;

CREATE TABLE character_aliases (
  id           INTEGER PRIMARY KEY,
  character_id INTEGER NOT NULL REFERENCES characters(id) ON DELETE CASCADE,
  alias        TEXT NOT NULL,
  alias_type   TEXT NOT NULL DEFAULT 'alias' CHECK (alias_type IN (
                 'alias','secret_identity','codename','title','translation','misspelling')),
  UNIQUE (character_id, alias)
);

CREATE INDEX ix_character_aliases_alias ON character_aliases(alias);
```

`first_appearance_issue_id` is spoiler-sensitive by nature. It is not shown to a profile whose
frontier is before that issue; see §13.

### 10.2 Appearances

```sql
CREATE TABLE character_appearances (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  character_id  INTEGER NOT NULL REFERENCES characters(id) ON DELETE CASCADE,
  issue_id      INTEGER NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
  appearance_type TEXT NOT NULL DEFAULT 'full' CHECK (appearance_type IN (
                    'full','cameo','flashback','mentioned','dream',
                    'alternate_reality','illusion','corpse','voice_only')),
  is_first_appearance  INTEGER NOT NULL DEFAULT 0 CHECK (is_first_appearance IN (0,1)),
  is_death             INTEGER NOT NULL DEFAULT 0 CHECK (is_death IN (0,1)),
  is_return            INTEGER NOT NULL DEFAULT 0 CHECK (is_return IN (0,1)),
  significance  INTEGER,          -- 0..3, optional
  note          TEXT,
  source_id     INTEGER REFERENCES metadata_sources(id),
  UNIQUE (character_id, issue_id, appearance_type)
);

CREATE INDEX ix_appearances_issue ON character_appearances(issue_id);
CREATE INDEX ix_appearances_char  ON character_appearances(character_id, issue_id);
```

**Spoiler landmines in this table:**

- `is_death = 1` is one of the most spoiler-heavy facts in comics.
- `appearance_type='corpse'` was included to catch a common edge case, but consider whether it is
  needed; it is easy to get wrong. It is listed to force the decision, not to recommend it.
- `is_return` is a spoiler in the opposite direction ("they come back"). A death must not be
  shown as permanent to a reader who has not reached the return. This is why appearances are
  filtered by reveal anchor rather than merely hidden by a boolean.

Data volume warning: appearances are potentially enormous (a character in a thousand issues).
This table must be loaded incrementally (by series or by order) in the UI. Do not fetch all
appearances for a character at once.

### 10.3 Relationships

```sql
CREATE TABLE relationship_types (
  id            INTEGER PRIMARY KEY,
  code          TEXT NOT NULL UNIQUE,     -- 'parent_of', 'ally_of', 'romantic_with'
  forward_label TEXT NOT NULL,
  reverse_label TEXT NOT NULL,
  is_symmetric  INTEGER NOT NULL DEFAULT 0 CHECK (is_symmetric IN (0,1))
);

CREATE TABLE character_relationships (
  id                  INTEGER PRIMARY KEY,
  uuid                TEXT NOT NULL UNIQUE,
  character_a_id      INTEGER NOT NULL REFERENCES characters(id) ON DELETE CASCADE,
  character_b_id      INTEGER NOT NULL REFERENCES characters(id) ON DELETE CASCADE,
  relationship_type_id INTEGER NOT NULL REFERENCES relationship_types(id),
  status              TEXT NOT NULL DEFAULT 'active' CHECK (status IN (
                        'active','former','unknown','secret')),
  is_spoiler          INTEGER NOT NULL DEFAULT 0 CHECK (is_spoiler IN (0,1)),
  reveal_issue_id     INTEGER REFERENCES issues(id),
  description         TEXT,
  source_id           INTEGER REFERENCES metadata_sources(id)
);

CREATE INDEX ix_rel_a ON character_relationships(character_a_id);
CREATE INDEX ix_rel_b ON character_relationships(character_b_id);
```

**No SQL-level direction check.** SQLite forbids subqueries in `CHECK` constraints, so a rule like
"store symmetric relationships with `MIN(id)` as A and `MAX(id)` as B" cannot be enforced
declaratively without a trigger. Normalise direction in Rust (a single repository function), add
a test, and optionally enforce with a trigger later. Documenting the attempted constraint is
better than shipping one that SQLite silently rejects at migration time.

`reveal_issue_id` is essential: a secret identity or a hidden parentage is a spoiler until a
specific issue. A relationship without a reveal anchor must be treated as safe only if it is
explicitly marked non-spoiler.

## 11. Story arcs, events, and timelines

### 11.1 Arcs

An arc is a narrative unit that can cross series and publishers.

```sql
CREATE TABLE arcs (
  id           INTEGER PRIMARY KEY,
  uuid         TEXT NOT NULL UNIQUE,
  title        TEXT NOT NULL,
  sort_title   TEXT,
  description  TEXT,
  franchise_id INTEGER REFERENCES franchises(id),
  arc_type     TEXT NOT NULL DEFAULT 'story' CHECK (arc_type IN (
                 'story','crossover','event_tie_in','saga','backup','annual_event')),
  start_issue_id INTEGER REFERENCES issues(id),
  end_issue_id   INTEGER REFERENCES issues(id),
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  deleted_at   INTEGER
);

CREATE TABLE arc_issues (
  arc_id      INTEGER NOT NULL REFERENCES arcs(id) ON DELETE CASCADE,
  issue_id    INTEGER NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
  position    INTEGER NOT NULL DEFAULT 0,
  is_core     INTEGER NOT NULL DEFAULT 1 CHECK (is_core IN (0,1)),
  note        TEXT,
  PRIMARY KEY (arc_id, issue_id)
);

CREATE INDEX ix_arc_issues_issue ON arc_issues(issue_id, arc_id);
```

**`start_issue_id`/`end_issue_id` are convenience only.** The authoritative membership and order
are in `arc_issues`. Arcs with a reading position that is not publication order need `position`,
which is present.

**Criticism:** an arc and a "story arc reading order" overlap heavily. That is intentional:
`arc` is canonical metadata, `reading_order` is a user-visible sequence that may add tie-ins,
skip optional issues, or include non-canon material. Do not merge them.

### 11.2 Events

An event is a publisher-level crossover with a brand and a schedule.

```sql
CREATE TABLE events (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  title         TEXT NOT NULL,
  publisher_id  INTEGER REFERENCES publishers(id),
  franchise_id  INTEGER REFERENCES franchises(id),
  start_year    INTEGER,
  end_year      INTEGER,
  description   TEXT,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted_at    INTEGER
);

CREATE TABLE event_issues (
  event_id    INTEGER NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  issue_id    INTEGER NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
  role        TEXT NOT NULL DEFAULT 'tie_in' CHECK (role IN (
                'core','tie_in','lead_in','aftermath','optional','reprint')),
  position    INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (event_id, issue_id)
);

CREATE INDEX ix_event_issues_issue ON event_issues(issue_id, event_id);
```

**Why events are separate from arcs:** an event is a publication/editorial construct with a brand
and often a spine; an arc is a narrative unit. They frequently overlap, and collapsing them makes
both worse. An event that is also one big story gets both an event row and an arc row, linked
through their issue membership.

### 11.3 Timelines

A timeline orders entities for a purpose: publication history, in-universe chronology, or a
franchise's recommended reading.

```sql
CREATE TABLE timelines (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  title         TEXT NOT NULL,
  timeline_type TEXT NOT NULL CHECK (timeline_type IN (
                  'publication','in_universe','recommended','character','franchise')),
  franchise_id  INTEGER REFERENCES franchises(id),
  anchor_date   TEXT,               -- in-universe era label/date, free text or ISO
  description   TEXT,
  is_generated  INTEGER NOT NULL DEFAULT 0 CHECK (is_generated IN (0,1)),
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted_at    INTEGER
);

CREATE TABLE timeline_entries (
  id           INTEGER PRIMARY KEY,
  uuid         TEXT NOT NULL UNIQUE,
  timeline_id  INTEGER NOT NULL REFERENCES timelines(id) ON DELETE CASCADE,
  position     REAL NOT NULL,
  entity_type  TEXT NOT NULL CHECK (entity_type IN ('issue','event','arc','series')),
  entity_id    INTEGER NOT NULL,
  label        TEXT,
  date_label   TEXT,
  note         TEXT
);

CREATE INDEX ix_timeline_entries ON timeline_entries(timeline_id, position);
```

**Overlap criticism:** `timelines` and `reading_orders` both order things. They are kept separate
because:

- a timeline may order entities that cannot be read (events, arcs, eras),
- a timeline may be generated and refreshed, whereas a user order is manually curated,
- timelines do not track per-profile progress.

If both grow into the same thing, merge them later. Do not pre-emptively unify, because the
progress and generation semantics differ. **This is a recommendation (R14).**

## 12. Metadata sources, identifiers, and provenance

### 12.1 Sources

```sql
CREATE TABLE metadata_sources (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  code          TEXT NOT NULL UNIQUE,      -- 'comicinfo', 'filename', 'provider_x', 'user'
  name          TEXT NOT NULL,
  source_type   TEXT NOT NULL CHECK (source_type IN (
                  'embedded','filesystem','provider','user','import','derived')),
  base_url      TEXT,
  requires_auth INTEGER NOT NULL DEFAULT 0 CHECK (requires_auth IN (0,1)),
  is_enabled    INTEGER NOT NULL DEFAULT 1 CHECK (is_enabled IN (0,1)),
  priority      INTEGER NOT NULL DEFAULT 100,  -- lower wins on conflict
  rate_limit_per_min INTEGER,
  notes         TEXT,
  created_at    INTEGER NOT NULL
);
```

Seed rows are inserted by the migration. Fixed, namespaced UUIDs are used so every installation
and every export agrees on the identity of these reference rows:

```sql
INSERT INTO metadata_sources (uuid, code, name, source_type, priority, created_at) VALUES
  ('00000000-0000-4000-8000-000000000001', 'user',      'User edit',       'user',       0,   0),
  ('00000000-0000-4000-8000-000000000002', 'comicinfo', 'ComicInfo.xml',   'embedded',   10,  0),
  ('00000000-0000-4000-8000-000000000003', 'filename',  'Filename parser', 'filesystem', 20,  0),
  ('00000000-0000-4000-8000-000000000004', 'import',    'Imported file',   'import',     30,  0),
  ('00000000-0000-4000-8000-000000000005', 'derived',   'Derived',         'derived',    90,  0);
```

Fixed seed UUIDs are a deliberate exception to "generate UUIDs in the application": reference
rows must be identifiable across installations and exports. They are constants in the migration,
not random values.

Provider rows are created at runtime or by migration when a provider adapter is added. `user` has
the lowest priority number and therefore always wins.

### 12.2 External identifiers

```sql
CREATE TABLE external_ids (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  entity_type   TEXT NOT NULL CHECK (entity_type IN (
                  'publisher','series','issue','creator','character','arc','event',
                  'franchise','collection')),
  entity_id     INTEGER NOT NULL,
  source_id     INTEGER NOT NULL REFERENCES metadata_sources(id),
  external_id   TEXT NOT NULL,
  external_url  TEXT,
  confidence    REAL NOT NULL DEFAULT 1.0 CHECK (confidence BETWEEN 0 AND 1),
  fetched_at    INTEGER NOT NULL,
  UNIQUE (entity_type, entity_id, source_id, external_id)
);

CREATE INDEX ix_external_ids_lookup ON external_ids(source_id, external_id);
CREATE INDEX ix_external_ids_entity ON external_ids(entity_type, entity_id);
```

**Why not per-table columns (`comicvine_id`, `metron_id`, ...):** the number of sources grows, and
each new source would require a schema migration across five tables. A generic table is additive.
The cost is a polymorphic `entity_type`/`entity_id` pair with no FK enforcement; that is why it is
restricted to a small, stable entity set and validated in Rust.

### 12.3 Field provenance

The simplest approach that still supports "why is this field wrong?":

```sql
CREATE TABLE field_provenance (
  id            INTEGER PRIMARY KEY,
  entity_type   TEXT NOT NULL CHECK (entity_type IN (
                  'publisher','series','issue','creator','character','arc','event')),
  entity_id     INTEGER NOT NULL,
  field_name    TEXT NOT NULL,
  source_id     INTEGER NOT NULL REFERENCES metadata_sources(id),
  value_hash    TEXT,               -- hash of the value that was set, to detect drift
  confidence    REAL CHECK (confidence IS NULL OR confidence BETWEEN 0 AND 1),
  first_seen_at INTEGER NOT NULL,
  last_seen_at  INTEGER NOT NULL,
  UNIQUE (entity_type, entity_id, field_name, source_id)
);

CREATE INDEX ix_provenance_entity ON field_provenance(entity_type, entity_id);
```

**This does not store every value.** Storing a full audit of every provider value for every field
is expensive and rarely used. Instead:

- the current value lives on the entity;
- provenance records *which source last set it* and *when*;
- `metadata_snapshots` keeps the raw provider payload for re-parsing and diffing;
- user edits set `metadata_locked`/`source_id='user'` and are never overwritten automatically.

**Criticism:** `value_hash` is only useful if you compute it consistently (normalised value).
Define the normalisation per field or omit the column. A half-implemented provenance system is
worse than none.

### 12.4 Metadata snapshots

```sql
CREATE TABLE metadata_snapshots (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  source_id     INTEGER NOT NULL REFERENCES metadata_sources(id),
  entity_type   TEXT NOT NULL,
  entity_id     INTEGER,
  external_id   TEXT,
  request_hash  TEXT NOT NULL,
  payload       BLOB NOT NULL,        -- gzip or zstd compressed JSON
  content_type  TEXT NOT NULL DEFAULT 'application/json',
  fetched_at    INTEGER NOT NULL,
  expires_at    INTEGER,
  UNIQUE (source_id, request_hash, fetched_at)
);

CREATE INDEX ix_snapshots_entity ON metadata_snapshots(entity_type, entity_id);
CREATE INDEX ix_snapshots_lookup ON metadata_snapshots(source_id, external_id);
```

Snapshots are **cache/audit data**, not authoritative. They may be pruned. Keep the most recent
one per entity per source plus any snapshot referenced by a manual decision.

### 12.5 Match proposals

Matching should produce proposals, not silent writes:

```sql
CREATE TABLE match_proposals (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  file_id       INTEGER NOT NULL REFERENCES library_files(id) ON DELETE CASCADE,
  issue_id      INTEGER REFERENCES issues(id) ON DELETE CASCADE,
  source_id     INTEGER NOT NULL REFERENCES metadata_sources(id),
  confidence    REAL NOT NULL CHECK (confidence BETWEEN 0 AND 1),
  reasons       TEXT,               -- JSON array of human-readable match reasons
  status        TEXT NOT NULL DEFAULT 'pending' CHECK (status IN (
                  'pending','accepted','rejected','superseded','expired')),
  created_at    INTEGER NOT NULL,
  decided_at    INTEGER
);

CREATE INDEX ix_proposals_file ON match_proposals(file_id, status);
```

This table makes automatic matching auditable and reversible. Rejecting a proposal must not
recreate it on every scan: keep the rejection and suppress re-proposal for the same fingerprint
unless the user asks for a rematch.

## 13. Spoiler protection in the data model

Spoiler protection is not a `hidden` boolean on a table. It is a **visibility predicate** applied
to facts, evaluated against a profile's position in one or more sequences.

### 13.1 The core concept: a reveal anchor

Every spoilable fact must answer: *"from which point is this fact safe to show?"*

There are three possible shapes:

| Shape | Example | Representation |
| --- | --- | --- |
| Single issue | "The butler did it" in issue #12 | `reveal_issue_id` |
| Set of issues | Character dies in #5, returns in #40 | reveal anchor + optional "safe again" handling |
| Position in a reading order | A custom order that reads a prequel first | `reveal_order_item_id` / position |

A single `reveal_issue_id` handles the common case. It fails for re-reading orders and for facts
that become safe at a point in a curated order that is not publication order. The model therefore
uses **abstract spoiler facts** rather than per-table columns.

### 13.2 Spoiler facts

```sql
CREATE TABLE spoiler_facts (
  id            INTEGER PRIMARY KEY,
  uuid          TEXT NOT NULL UNIQUE,
  subject_type  TEXT NOT NULL CHECK (subject_type IN (
                  'issue','series','arc','event','character','relationship',
                  'collection','creator','order_item','annotation','text')),
  subject_id    INTEGER NOT NULL,
  fact_type     TEXT NOT NULL,       -- open vocabulary: 'synopsis','death','identity',
                                     -- 'appearance','relationship','ending','cameo', ...
  payload       TEXT,                -- JSON: the actual sensitive statement(s)
  reveal_issue_id INTEGER REFERENCES issues(id),
  reveal_order_id INTEGER REFERENCES reading_orders(id),
  reveal_position REAL,              -- position within reveal_order_id
  severity      TEXT NOT NULL DEFAULT 'major' CHECK (severity IN (
                  'minor','moderate','major','critical')),
  is_global     INTEGER NOT NULL DEFAULT 0 CHECK (is_global IN (0,1)),
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  CHECK (reveal_issue_id IS NOT NULL OR reveal_order_id IS NOT NULL OR is_global = 1)
);

CREATE INDEX ix_spoiler_facts_subject ON spoiler_facts(subject_type, subject_id);
CREATE INDEX ix_spoiler_facts_reveal_issue ON spoiler_facts(reveal_issue_id);
CREATE INDEX ix_spoiler_facts_reveal_order ON spoiler_facts(reveal_order_id, reveal_position);
```

**Criticism of this design:**

- `subject_type`/`subject_id` is polymorphic and unenforced, like `collection_items`. It is
  deliberate: the alternative is one spoiler table per entity, which multiplies joins and makes
  a single "is this visible?" query impossible.
- `payload` JSON means the contents are not searchable by SQL unless FTS is added. For spoiler
  filtering we mostly need the *predicate*, not full-text search inside the fact, so this is
  acceptable. Full-text over synopses uses a dedicated FTS table (§14) with its own reveal
  metadata.
- A fact with `reveal_issue_id` and a fact with `reveal_order_id` are not equivalent. A profile
  can be past issue #10 in one series but in the middle of an order that places issue #10 later.
  The visibility rule must check **both** anchors and take the more conservative answer.

### 13.3 The spoiler frontier

Efficiency requires an indexable notion of "how far has this profile read".

```sql
CREATE TABLE spoiler_frontier (
  profile_id       INTEGER NOT NULL REFERENCES reader_profiles(id) ON DELETE CASCADE,
  scope_type       TEXT NOT NULL CHECK (scope_type IN (
                     'global','publisher','franchise','series','order','character')),
  scope_id         INTEGER NOT NULL DEFAULT 0,  -- 0 means "global"; no FK by design
  -- Issue-based position (used when scope is series/publisher/franchise/global)
  issue_sort_year  INTEGER,          -- cover year, coarse
  issue_number_sort REAL,
  issue_id         INTEGER REFERENCES issues(id),
  -- Order-based position (used when scope is order)
  order_position   REAL,
  updated_at       INTEGER NOT NULL,
  PRIMARY KEY (profile_id, scope_type, scope_id)
);
```

This is a **denormalised projection** recomputed when progress changes. It is not authoritative;
it exists so a candidate row can be compared against a numeric frontier without joining progress
for every result.

**Severe caveat:** a single issue can advance one series and not another. "Global frontier" is
only meaningful if it is derived from a curated reading order, not from the maximum page read.
Do not ship a global frontier computed from "the furthest issue the user has opened" unless the
UI is explicit that it is approximate. This is one of the hardest parts of the feature and
deserves its own design pass before implementation. **Decision Q5.**

### 13.4 Safer alternative for v1 (recommended)

For the first release, use **explicit set membership** instead of a numeric frontier:

```sql
CREATE TABLE spoiler_read_marks (
  profile_id     INTEGER NOT NULL REFERENCES reader_profiles(id) ON DELETE CASCADE,
  issue_id       INTEGER NOT NULL REFERENCES issues(id) ON DELETE CASCADE,
  read_at        INTEGER NOT NULL,
  PRIMARY KEY (profile_id, issue_id)
);

CREATE INDEX ix_read_marks_issue ON spoiler_read_marks(issue_id);
```

A fact is visible if `reveal_issue_id IS NULL OR is_global = 1 OR reveal_issue_id IN (SELECT
issue_id FROM spoiler_read_marks WHERE profile_id = ?)`.

This is correct, simple, and indexable. It is conservative: it does not infer "safe" from a
reading order unless the order's items are also marked read. It cannot handle "spoiler-safe up to
a point inside an issue", but that is a rare requirement. Start here; layer order-aware logic on
top only when the need is proven. **This is the recommended implementation (R15).**

### 13.5 Text and synopsis spoilers

Synopses, descriptions, notes, and provider summaries are the most common leak. Storing them as
plain columns on `issues`/`arcs`/`events` means any query that selects `*` leaks them.

Two options:

- **Keep the column but never select it without the policy.** Requires discipline and is easy to
  break with a future query.
- **Split spoiler-sensitive text into its own table**, so a normal issue query literally cannot
  read it.

Recommended:

```sql
CREATE TABLE spoilable_texts (
  id              INTEGER PRIMARY KEY,
  uuid            TEXT NOT NULL UNIQUE,
  subject_type    TEXT NOT NULL CHECK (subject_type IN (
                    'issue','series','arc','event','character','relationship','creator')),
  subject_id      INTEGER NOT NULL,
  text_kind       TEXT NOT NULL CHECK (text_kind IN (
                    'synopsis','description','bio','note','ending','preview')),
  body            TEXT NOT NULL,
  reveal_issue_id INTEGER REFERENCES issues(id),
  reveal_order_id INTEGER REFERENCES reading_orders(id),
  reveal_position REAL,
  source_id       INTEGER REFERENCES metadata_sources(id),
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL
);

CREATE INDEX ix_spoilable_subject ON spoilable_texts(subject_type, subject_id, text_kind);
```

Then `issues.synopsis` should either be removed or marked as a non-spoiler short blurb. Having
both a `synopsis` column on `issues` and a `spoilable_texts` row is a guaranteed inconsistency.
**Decision Q6:** keep a short safe blurb on `issues` and put the full synopsis in
`spoilable_texts`, or remove the column entirely. The former is recommended for UI performance
(one join fewer for a safe field).

### 13.6 Search and spoilers

Search is the classic leak: a result snippet, a character name, or an arc title can reveal a
future event. The rule is:

> One spoiler filter runs before any result text is generated, and the filter is the same code
> path used for detail views.

Implementation consequences:

- The FTS table stores `reveal_issue_id` (or a join to the source row) and the query joins
  against `spoiler_read_marks` for the active profile.
- Snippet generation must run **after** filtering. SQLite's `snippet()` on a filtered result set
  is fine; generating snippets and then hiding rows is not.
- Character/arc names themselves can spoil. A character whose first appearance is after the
  frontier must not appear in "characters in this issue" lists, and an arc title like "The Death
  of X" must not appear before the reveal issue. This means **names are not automatically safe**.
  The model supports it through `spoiler_facts` and `spoilable_texts`; the rule for v1 is:
  hide entities whose reveal anchor is after the frontier, rather than trying to partially mask
  their names.

### 13.7 What the model cannot solve

- **Readers who want a different order than the one the app knows.** The frontier is only as good
  as the chosen scope. UI must say which sequence a spoiler setting follows.
- **Spoilers from outside the library.** A provider summary for an unowned issue can spoil a
  series the user owns. Do not show related-issue summaries by default.
- **Inference.** A reader can infer a death from an unexplained absence. No data model fixes that.
- **Partial-issue progress in a book with several issues.** `spoiler_read_marks` is per issue. If
  one file contains issues 1–3 and the user is on page 40, the model cannot know which issue that
  is unless the page offsets are trusted. Use `file_issue_map.page_offset` to translate, and mark
  the boundary conservatively (do not mark issue 2 as read until its first page is passed).

### 13.8 Open decision: default spoiler mode

`reader_profiles.spoiler_mode` defaults to `'strict'`. That is safe but can make a new library feel
empty: synopses hidden, characters hidden, arcs hidden. The alternative is a first-run choice
("I have read nothing" vs "I have read up to X"). **Decision Q7.**

## 14. Full-text search

```sql
CREATE VIRTUAL TABLE search_index USING fts5(
  entity_type UNINDEXED,
  entity_id   UNINDEXED,
  title,
  body,
  aliases,
  tokenize = 'unicode61 remove_diacritics 2'
);
```

Design notes:

- One FTS table for all searchable entities, with `entity_type`/`entity_id` columns.
- `title` and `body` are separate columns so ranking can weight titles (`bm25(search_index, 10.0, 1.0)`).
- The index contains only text that is safe to *match*. Spoiler filtering is applied to results
  by joining the source row, not by omitting text from the index. Omitting spoiler text from the
  index would make search silently miss safe results (for example, an arc name that is safe for
  a reader past the reveal).
- Rebuild with `INSERT INTO search_index(search_index) VALUES('rebuild')` after a schema or
  tokenizer change.
- Update in the same transaction as catalog writes. A stale index is acceptable; a corrupted
  index is not — provide a rebuild command in diagnostics.

Search over issue numbers, years, and publishers should use normal indexed queries, not FTS.

## 15. Preferences and settings storage

There are three levels of preference:

| Level | Storage | Examples |
| --- | --- | --- |
| Application | `app_settings` key/value | theme, language, provider endpoints (non-secret) |
| Profile | `reader_profiles` columns + JSON | spoiler mode, default reading mode |
| Per-series / per-file overrides | dedicated tables | delete-after-read, spread behaviour, brightness |

```sql
CREATE TABLE app_settings (
  key        TEXT PRIMARY KEY,
  value      TEXT NOT NULL,        -- JSON
  updated_at INTEGER NOT NULL
);

CREATE TABLE series_preferences (
  profile_id       INTEGER NOT NULL REFERENCES reader_profiles(id) ON DELETE CASCADE,
  series_id        INTEGER NOT NULL REFERENCES series(id) ON DELETE CASCADE,
  reading_mode     TEXT,
  read_direction   TEXT CHECK (read_direction IN ('ltr','rtl')),
  fit_mode         TEXT CHECK (fit_mode IN ('width','height','page','actual')),
  double_page_mode TEXT CHECK (double_page_mode IN ('auto','off','on')),
  transition       TEXT,
  brightness       REAL,
  gamma            REAL,
  extra            TEXT,           -- JSON for future per-series options
  PRIMARY KEY (profile_id, series_id)
);

CREATE TABLE file_preferences (
  profile_id     INTEGER NOT NULL REFERENCES reader_profiles(id) ON DELETE CASCADE,
  file_id        INTEGER NOT NULL REFERENCES library_files(id) ON DELETE CASCADE,
  reading_mode   TEXT,
  fit_mode       TEXT,
  page_spread_map TEXT,            -- JSON: explicit spread pairings / overrides
  extra          TEXT,
  PRIMARY KEY (profile_id, file_id)
);
```

**Criticism:** `extra` JSON columns are where schemas go to die. Use them only for display options
that are not queried and are safe to discard if a version is downgraded. Anything that affects
reading logic (read direction, spread pairing) must be a real column with a check.

## 16. Indexing and query patterns

Expected hot queries and their indexes:

| Query | Index |
| --- | --- |
| Bookshelf: recently read | `ix_progress_profile_recent` |
| Series list by title | `ix_series_sort` |
| Issues in a series | `ix_issues_series_sort` |
| Unmatched files | `ix_files_status` |
| File by root+path | `ux` on `(root_id, rel_path)` |
| Page manifest | `file_pages` PK |
| Reading order items | `ix_order_items_order` |
| Order progress | PK |
| Spoiler check | `spoiler_read_marks` PK + `ix_read_marks_issue` |
| Issue by external ID | `ix_external_ids_lookup` |
| Search | FTS5 |
| Character appearances by issue | `ix_appearances_issue` |

Rules:

- Every list query has a stable `ORDER BY` with a unique tiebreaker (usually `id`), or pagination
  will duplicate/skip rows.
- Prefer keyset pagination (`WHERE (sort_col, id) > (?, ?) ORDER BY sort_col, id LIMIT ?`) for
  large lists. Offset pagination degrades on deep pages.
- Never join page manifests or appearances into list queries; load them on detail.
- `EXPLAIN QUERY PLAN` any new query that touches more than one large table.

## 17. Database lifecycle and migrations

### 17.1 Migration rules

- One numbered migration per schema change, applied in order, inside a transaction.
- Every migration is tested against a copy of a real database at the previous version, not only
  against an empty database.
- Never edit an applied migration. Add a new one.
- Destructive changes (dropping a column/table) use the SQLite rebuild pattern: create new table,
  copy data, drop old, rename. Verify foreign keys are disabled for the rebuild and re-enabled
  afterwards, then run `PRAGMA foreign_key_check`.
- Seed reference data (metadata sources, relationship types) in migrations so every installation
  is consistent.
- The application refuses to open a database whose `user_version` is newer than the binary,
  rather than guessing.

### 17.2 Versioning for exports

Reading orders, collections, and library metadata exports must carry an explicit format version
and UUIDs. Never export integer IDs; they are local and unstable. A re-import on another machine
must resolve by UUID first, then external ID, then a user-reviewed match.

### 17.3 Backups

- Before migration: `VACUUM INTO` a timestamped backup.
- Periodic backup: optional, user-controlled, to a chosen folder.
- Backup files must not be confused with the live database by the sync/cloud detection warning.
- Test restore as part of the migration test suite.

## 19. Rejected alternatives

Recorded so they are not re-litigated without new information.

| Alternative | Why rejected |
| --- | --- |
| One `comics` table containing both file and issue data | Loose files, multi-issue files, and rematching all break; forces every file to have metadata |
| `issues.series_id` + `series.reading_order` integer | Cannot express cross-publisher orders; every reorder rewrites the series |
| Reading order as a JSON array on the series | Not queryable, no progress tracking, no cross-series items |
| Characters as tags | Loses relationship types, reveal anchors, and appearance metadata |
| A single `spoiler_level` integer per issue | Cannot represent "safe in one order, unsafe in another"; encourages leaks |
| Storing page images as BLOBs in SQLite | Database bloat, WAL amplification, no range requests, no cache control |
| Absolute file paths on `library_files` | Root moves, relinking, and portability all break |
| Polymorphic `entity_id` everywhere | Acceptable in three places (collections, external IDs, spoiler facts) with app-level integrity; unacceptable for the core catalog |
| Using issue numbers as identity | Specials, decimals, variants, and renumbering make this unreliable |
| Multiple databases per library | Complicates cross-library search, reading orders, and character data |
| Storing progress only per issue | Loose files and multi-issue files become unreadable/untrackable |

## 21. Summary

- **Files are the durable, offline-readable unit.** Issues are optional catalog identities linked
  through `file_issue_map`, which supports many-to-many and multi-issue files.
- **Reading orders are independent ordered lists** of issue or file references, with progress
  per profile. They can mix publishers and series by construction; nothing ties them to a series.
- **Spoilers are modelled as facts with reveal anchors** plus an explicit set of read marks. The
  conservative v1 implementation is simple, indexable, and hard to leak.
- **Metadata is provenance-aware.** User edits win, provider data is cached and snapshotted, and
  matching produces reviewable proposals rather than silent writes.
- **Character, arc, event, and timeline tables exist early** so later features are additive.
- The main data-model risks are the many-to-many file/issue mapping, spoiler semantics across
  independent orders, and polymorphic reference tables. Each is documented with its limits and a
  conservative implementation path.
